# ESP32-S3 Home Spine 4.2 美术制作规范（阶段版）

版本：0.1  
目标：在当前 ESP32-S3 固件和 320×320 屏幕上，让角色在实际设备上稳定达到约 24 FPS。

这是一份基于当前固件和 `test2` 实测结果的阶段版规范。它已经可以作为美术制作的第一道筛选标准；骨骼、Mesh 和透明叠加的最终硬上限，还应使用更多只改变一个因素的角色包继续验证。

## 1. 固定运行条件

- 屏幕：320×320 像素。
- Spine runtime：4.2，接受 4.2.x 导出数据。
- 贴图：RGBA8888、带 Alpha、单个 `texture.png`。
- 在线角色包：`spine` 分区最大 4 MiB。
- 当前 Home 目标帧率：30 FPS；当前渲染循环的稳定上限约为 24～25 FPS，因此本规范暂以 24 FPS 作为验收目标。
- 当前角色通常处在 320×240 的参考场景区域内，屏幕底部和对话卡片需要保留界面空间。

## 2. 分辨率、图集尺寸和屏幕显示尺寸

`872×872` 是 PNG 图集页的像素尺寸，也就是贴图分辨率。它不是角色在屏幕上的显示宽高，也不是设备屏幕分辨率。

当前设备的显示区域是 `320×320`。角色在屏幕上的大小由 Spine skeleton 的坐标范围、`role.json` 中的 `scale` 和运行时位置共同决定。`test2` 的 `scale` 是 `0.08`，所以 872 像素的图集可以被缩小后显示成一个较小的角色。

PNG 仍然会按完整图集解码：

```text
872 × 872 × 4 = 3,041,536 字节
```

因此，角色看起来小，并不代表设备只处理了很小的图片。

正常 Home 模式建议把运行时角色的实际 skeleton 高度控制在约 200～240 像素，并给对话区、状态图标和边缘留出空间。若确实要覆盖整个 320×320 画面，应把它作为单独的全屏角色配置测试；贴图页不必强制做成 320×320，但角色投影到屏幕后的有效范围必须在 320×320 内。

### 透明重叠

Spine JSON 和 atlas 能告诉我们附件数量、Mesh 和纹理区域，但不能直接给出“同一个屏幕像素被绘制了几次”。透明重叠取决于某个动作的实际姿势、附件投影位置、附件矩形中的透明像素和绘制顺序。

当前代码也没有输出逐像素 overdraw 统计。因此 `test2` 的透明重叠目前只能判定为需要重点关注，不能诚实地写成一个精确数字。若要得到精确值，需要在软件光栅器中增加 overdraw 计数，或对每个动作采集附件投影后的覆盖次数。

## 4. 这次低帧率的原因

日志中 `test2` 的表现是：

```text
fps=6～7
render=115～131 ms
spi=约 10～20 ms
```

24 FPS 每帧预算约为 41.7 ms。`render` 已经达到 115～131 ms，并且远高于 SPI 刷屏时间，所以主要问题是 CPU 软件渲染负载，不是代码把角色固定限制在 6～7 FPS。

当前代码确实有一个独立的帧率限制因素：外层任务每 10 ms 调用一次，引擎内部按 34 ms 间隔更新，所以简单角色通常稳定在约 24～25 FPS。这可以解释之前小角色的 24～25 FPS，但不能解释 `test2` 的 6～7 FPS。`test2` 是实际渲染计算超过帧预算后自然掉帧。

当前引擎每帧会执行动画状态更新、骨骼世界变换、Mesh 顶点计算，并在 CPU 上逐像素进行三角形光栅化和 Alpha 混合。`test2` 同时具备 26 个 Mesh、9,026 个顶点、5,817 个三角形和 29 个 Physics 约束，因此属于明显超出当前 24 FPS 目标的角色。

## 5. 给美术人员的第一版限制

下面的数值是为了避免再次接近 `test2` 的失败区间而制定的阶段性生产值。它们不是已经逐项扫出的数学上限；每次固件或渲染器改变后，都需要重新在真机验证。

### 必须满足

- 使用 Spine 4.2.x 导出。
- 必须包含固件需要的动画名：`idle`、`talk_start`、`delight`、`suprise`、`action`。
- 必须使用 RGBA8888 Alpha PNG。
- 建议只使用 1 张 atlas page 和 1 个 `texture.png`。
- 角色包总大小不超过 4 MiB。
- 不使用 Clipping attachment。
- 不使用 Screen blend mode。
- 不使用 Dark Tint / RGBA2 双颜色。
- 生产角色暂不使用 Physics 约束。当前 4.2 runtime 能处理 Physics，但 `test2` 的 29 个 Physics 约束会增加每帧 CPU 工作，不适合在尚未完成单变量测试前作为常规美术特性。

### 建议值

| 项目 | 建议值 | 说明 |
|---|---:|---|
| atlas page | 不超过 512×512 | 872×872 已实测为 6～7 FPS 失败样本 |
| 解码后单张 RGBA 贴图 | 不超过约 1 MiB | 512×512×4 约 1 MiB |
| 骨骼 | 不超过 40 | `test2` 为 78 |
| slot | 不超过 20 | `test2` 为 32 |
| Mesh attachment | 不超过 8 | `test2` 为 26 |
| 所有 Mesh 顶点合计 | 不超过约 2,000 | `test2` 为 9,026 |
| 单个 Mesh 顶点 | 不超过 300 | `test2` 最大为 1,298 |
| 所有 Mesh 三角形合计 | 不超过约 1,200 | `test2` 为 5,817 |
| IK + Transform 约束 | 不超过 4 | `test2` 合计为 8 |
| Physics 约束 | 0 | 便于保持帧率稳定 |
| 每个动作时间线组 | 不超过 25 | 这是次要限制，仍需看 Mesh 和实际像素量 |
| 每个动作关键帧 | 不超过 150 | 不包括曲线数组本身的控制数值 |
| 动画数量 | 5 个目标动作 | 备用动画可保留，但不要用数量代替复杂度测试 |
| 单个动作时长 | 建议不超过 3 秒 | 主要影响资源和切换体验，不是首要帧率指标 |

透明效果方面，建议美术避免全屏烟雾、光晕、阴影和多层半透明装饰；把透明边缘裁紧，隐藏不用的附件，减少同一屏幕区域的重复覆盖。当前代码会跳过完全透明的附件，但这不等于半透明附件没有绘制成本。最终仍以最复杂动作在真机上的 24 FPS 验收为准。

## 6. 真机验收标准

一个角色包满足以下条件，才可以进入生产素材库：

- 开机成功，`.skel`、`.atlas` 和 PNG 都能解析、解码。
- 所有 5 个约定动作都能播放；缺少动作名的包退回修改。
- 设备稳定运行 10 分钟，整体 FPS 维持在约 24 FPS 或以上。
- 30 秒性能窗口内没有持续下降；不能只看一次平均值。
- `render` 不应接近或超过 41.7 ms；建议生产素材留出余量，控制在约 30～35 ms 以内。
- 不出现缺图、花屏、接缝、看门狗重启和内存分配失败。
- 加载后 PSRAM 仍有足够余量；建议保留至少 2 MiB 的运行时余量。
- OTA 包不超过 4 MiB。

## 7. 对当前 `test2` 的结论

`test2` 不应作为美术标准样本。它可以作为压力测试样本，因为它同时包含大图集、多个高顶点 Mesh、较多骨骼和大量 Physics 约束；但它的实际结果只有 6～7 FPS，已经不符合 24 FPS 生产目标。

更合适的下一轮测试是固定同一套 skeleton，只做三组变化：

1. 保留 skeleton 和动作，只把贴图降到 512 或 640，观察 PSRAM 和 `render` 的变化。
2. 保留贴图和显示大小，减少 Mesh 顶点，观察 `render` 的变化。
3. 保留 Mesh，关闭 Physics 和约束，观察 `render` 的变化。

这样才能把“贴图内存问题”和“每帧 CPU 运算问题”分开，最后再把本规范中的建议值收敛成真正的硬上限。
