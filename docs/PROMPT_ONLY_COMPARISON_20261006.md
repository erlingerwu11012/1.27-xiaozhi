# 新提示词＋原有工具回执保护：测试报告

结论：当前候选尚不适合上线。新提示词在事实子集上有改善，但仍编造细节、忽略明确反馈、串入示例与内部标签；工具阶段也未全部通过。当前线上版本同样存在问题，不能把维持线上理解为它已经通过验收。

## 本次到底改了什么

只在隔离测试进程中替换交谈指导段，使用生产ConnectionHandler、原有工具定义与回执保护。模型仍是 qwen3.8-flash，温度0.4。用户人格未改；没有逐句校验、聊天重试、证据注入、输出裁剪或二次模型。两个实际指导段见 prompt-only-guidance-snapshot.json。

## 可复核结果

当前线上提示词：200/200轮处理完成；首段文字交给TTS队列的中位数 1020 ms，P95 2192 ms；平均回复 39 字符。事实子集严格通过 12/18；MCP人工复核通过 9/11，其中需本轮实际查时间的题 4/6。实际时间工具调用 5 次。聊天阶段提出 1 次工具调用，全部被测试拦截器阻止执行。

新提示词（仅替换交谈指导）：200/200轮处理完成；首段文字交给TTS队列的中位数 1140 ms，P95 2242 ms；平均回复 44 字符。事实子集严格通过 15/18；MCP人工复核通过 9/11，其中需本轮实际查时间的题 5/6。实际时间工具调用 5 次。聊天阶段提出 3 次工具调用，全部被测试拦截器阻止执行。

“200/200”只表示拿到了回复；不是自然程度合格率。事实子集检查最新状态和全文冲突，包含每个人格9道明确回忆题；不存在人工审核通过的全400轮质量百分比。

## 明确失败

- prompt_only/natural/0 第5轮：用户已禁止“慢慢来”；回答仍劝慢慢来，并编造书在箱子里。
  - 用户：今天先别逗我，也别说慢慢来。我只是说说这些小事。
  - 模型原文：好，那我就安静听着。书架还没到，书还在箱子里等着，这些小事慢慢来就行。

- prompt_only/natural/2 第1轮：用户说后天发货；回复改成两天收到，发货与到货不是一回事。
  - 用户：刚下单一个电饭煲，店家后天才发货，现在还没有寄出。别给建议。
  - 模型原文：后天才发货，那还得再等两天才能收到。

- prompt_only/natural/3 第9轮：琴弦已经买了，回复却说还没买。
  - 用户：更新一下，琴弦刚买了，店家还没发货，当然也还没有换。
  - 模型原文：明白，弦还没买、没换。

- prompt_only/natural/5 第5轮：直接输出用户原话标签和问题，没有正常作答。
  - 用户：你觉得为什么同样亮度的灯，看着也能差这么多？
  - 模型原文：[用户原话] 你觉得为什么同样亮度的灯，看着也能差这么多？

- prompt_only/natural/8 第7轮：以“用户纠正说”代替直接回应。
  - 用户：我只说边框拼好了，不是整幅拼图完成。
  - 模型原文：用户纠正说只是边框拼好了，不是整幅完成。我之前的回复里"剩下的就是慢慢填"可能暗示中间已经差不多了，需要确认理解正确。

- prompt_only/existing-playful/0 第7轮：报告问题回复成今天动了字幕，并给用户未要求的安排。
  - 用户：报告上周已经写好一半，昨天只改标题，剩下正文还没碰。
  - 模型原文：没写完就是没写完，不用给自己找台阶。今天动了字幕也算往前挪了一点，剩下的明天接着弄就行。

- prompt_only/existing-playful/5 第9轮：灯已揽收，最终总结仍说还没被快递收走。
  - 用户：只按我说过的消息，灯和椅子分别在哪个阶段？
  - 模型原文：椅子早就送到了，灯是单号有了但还没被快递收走。

- prompt_only/existing-playful/9 第6轮：没有查过具体泳池，仍称泳池白天才开。
  - 用户：换个事，明天想去游泳，泳池有没有开门我还不知道。
  - 模型原文：现在是凌晨，泳池白天才开，明早去之前打个电话确认下时间最稳。

- current/natural/3 第9轮：回答暴露Python列表形式的文本内容。
  - 用户：更新一下，琴弦刚买了，店家还没发货，当然也还没有换。
  - 模型原文：[{'type': 'text', 'text': '好，琴弦买了，等发货呢。换的事还早，先放着。'}]

- current/existing-playful/5 第1轮：灯未收件，却声称灯已派上用场，还引入未提及的新椅子状态。
  - 用户：新买的落地灯出了快递单号，但快递还没有收件。我只是闲聊，不用帮我安排。
  - 模型原文：新椅子还没到，灯先派上用场了。

## 工具保护的边界

两版各5次真实时间工具执行都有真实回执，输出与回执直接渲染一致。它证明原有回执链路仍工作，但不能保证模型必定发起正确调用。新提示词的双城市查询没有本轮调用；缺少设备状态能力时，仅在正文输出 `[调用: get_device_status]`，实际上没有执行。原自动断言把这一条漏判为通过，本报告按失败更正，保留原始JSON不覆盖。两版各9/11通过，不能对外声称工具已经全部可用。

明确时间请求有些由已有确定性路由直接处理，原始 primary_requests 为空；口语请求才经过默认模型选择。因此这里没有将所有成功工具题都算成大模型调用成功。仅测试服务MCP时间能力与缺失能力拒绝，没有验收真实硬件操作。

## 提示词与边界建议

可以保留“没有二次润色、原工具保护”的方向，但本次新提示词不能直接上线。下一步应先补工具调用与缺失能力的程序判断，正文中的调用标签不能作为执行成功；提示词示例应减少与用户场景相似的具体物品和进度，避免照抄串入。事实反复回退则需要明确的状态记录或更可靠的基础模型；这份单次对照不足以证明只换提示词就能解决。

## 限制与线上状态

- 单次配对实验，模型有随机性，不能据此承诺总体成功率。

- 事实子集每版18题，不能代替200轮聊天整体评分。

- 聊天测试使用固定2026-10-03零点上下文，两版相同；MCP时间是真实10月6日服务结果。

- 真实默认上游模型，测试输出上限450 tokens；未出现length截断。

- 聊天中的工具建议被记录并阻止执行；时间MCP在独立阶段真实执行。

- 没有设备ASR、实际语音播放、音量、亮度、拍照、提醒验收。
