# ESP32-S3半身Spine完整制作指南（表格版）

适用：当前ESP32-S3、320×320屏幕、v2/combined固件、配置SPI 30 MHz。整理日期：2026-10-03。局部重画优化本轮取消，按现有引擎制作。

**这些区间是制作起点和实测扩展建议，不是硬件上下限。无需补足建议下限；各项上端不能同时使用并期待固定帧率。人物显示范围、图集尺寸、绘制面积和发送面积要分别看。**

## 1. 第一版直接采用的配置

| 项目 | 建议值／做法 | 说明 |
| --- | --- | --- |
| 目标 | 静置约8 FPS，清晰优先 | 适用当前ESP32-S3、320×320屏幕、v2/combined固件；不是保证帧率的规格。 |
| 构图 | 正面半身到腰部，水平居中，下沿贴底 | 为字幕预留空间；全部动作姿态都要检查，不只看初始姿态。 |
| 人物显示范围 | 先做180×240像素 | 屏幕参考x=70～250、y=80～320；保持人物比例，不强行拉伸。 |
| 脸部有效显示宽度 | 约60～80像素 | 指五官区域；头部连头发可先按80～100像素宽安排。 |
| 设备图集 | 单张512×512透明PNG起步 | 从原始分层重新打包；装得下可用512×256，不要求正方形。 |
| 基础结构 | 约60骨骼；物理≤10；可见Mesh≤15 | 可见总顶点≤800、总三角形≤1200；更简单也可以。 |
| 动作 | idle待机＋talk_start讲话 | 先做这两个，再逐项增加挥手、转头等动作。 |
| 当前刷新方式 | 保持现有引擎，本轮不改局部重画 | 全部可见Spine附件仍逐帧标记重画；后置像素差分主要减少屏幕发送量。 |

## 2. 显示范围与刷新量

| 项目 | 优先范围 | 扩大前需要知道 |
| --- | --- | --- |
| 人物宽度 | 160～200像素，初版180 | 200～220像素作为实测扩展区间；包含手、头发和服饰。 |
| 人物高度 | 220～260像素，初版240 | 240～280像素作为实测扩展区间；底部贴底仍要留动作安全余量。 |
| 人物占屏比例 | 180×240约占整屏42.2% | 你原先的160×240是宽1/2、高3/4，矩形面积占整屏37.5%；不是面积占3/4。 |
| 动作包围范围 | 所有动作都尽量留在初版构图内 | 尺寸指屏幕上的人物＋附件包围范围，不是PSD画布或图集尺寸。 |
| 原刷新区域 | 观察目标约30,000～40,000像素/帧 | 看dirty／original_pixels；180×240矩形为43,200像素，需结合实测，不是硬超标。 |
| 实际发送区域 | 观察目标约15,000～30,000像素/帧 | 看sent_pixels；变化分散时一个外接矩形会把中间未变化像素一起发送。 |
| 透明重叠 | 同一点的大范围半透明叠加尽量2～3层 | 不等于整个人物只能有3层；不透明遮挡也可能重复绘制。 |
| 特效位置 | 靠近人物，不做大范围分散特效 | 远处飘带、光效、粒子可能拉大刷新和发送矩形。 |
| 上下起伏 | 躯干稳定，必要时小幅变化 | 当前引擎不会因只有嘴动而自动只画嘴；整体面积仍是关键预算。 |

## 3. 骨骼、网格与约束预算

| 项目 | 最低需求 | 推荐初版 | 扩展／注意 |
| --- | --- | --- | --- |
| 骨骼（根） | 按功能需要，几根也可以 | 30～80；第一版约60 | 80～120需实测；不是硬件最大值。 |
| 物理约束（个） | 0 | 0～10 | 10～20先测；几束头发、少量衣服，不给每根细发都建物理链。 |
| IK约束（个） | 0 | 0～4 | 更多时单独测试，主要用于确实需要的关节。 |
| Transform约束（个） | 0 | 0～8 | 更多时单独测试，避免无必要的多层依赖。 |
| Path约束（个） | 0 | 初版先不用 | 确实需要时先验证当前导出、预检和渲染兼容性。 |
| 同时可见Mesh（个） | 0，可全用普通图片附件 | 0～20；第一版≤15 | 20～30先测；仅需要形变的部件使用Mesh。 |
| 同时可见总顶点（个） | 按可见附件需要，无需补足300 | 约300～800 | 800～1200先测；普通图片每张4个顶点也计入。 |
| 同时可见总三角形（个） | 按可见附件需要，无需补足400 | 约400～1200 | 1200～1800先测；普通图片每张2个三角形也计入。 |
| 每个加权顶点的骨骼影响数 | 按需要，通常至少绑定1根 | 优先1～2根 | 关节局部3～4根；去掉没有实际效果的微小权重。 |
| 可见附件总数 | 按角色拆分需要 | 只拆需要独立运动的部件 | 没有从日志验证出的统一最大值；避免把静态细节拆成大量小附件。 |
| 网格布点 | 轮廓、关节、需要弯曲的位置 | 先少量布点，按变形效果增加 | 图片细节不需要密集网格；紧贴轮廓也不能无限增加三角形。 |
| 未使用的资源 | 能不制作就不制作 | 去掉不用的下半身、道具、皮肤和动画 | 仅将附件透明不会移除其骨骼、约束和资源数据。 |

## 4. 清晰度、图集与解码内存

| 项目 | 推荐做法／数值 | 解释 |
| --- | --- | --- |
| 原画 | 保留高分辨率PSD和原始分层 | 设备版本从原始部件导出；不要反复缩小再放大。 |
| 有效部件分辨率 | 先按屏幕最大显示边长的约1～1.5倍 | 这里指部件实际有内容的像素，不是带透明空白的整张分层图。 |
| 脸部示例 | 显示宽70像素，可先留约80～112像素有效脸图 | 优先保障脸、眼、嘴、刘海和手；最后在320×320原生尺寸查看。 |
| 静态细节 | 睫毛、衣服细线等画进图片 | 不需要为每条细线建立独立骨骼或网格。 |
| 透明空白 | 修剪部件四周空白，紧凑打包 | 图集只装设备实际使用的部件和皮肤。 |
| 滤波 | 保持Linear／当前双线性滤波 | 清晰度指南不靠默认关闭滤波省时间。 |
| 部件间距 | 约2像素padding＋duplicate padding | 减少边缘采样串色；按原尺寸和导出结果检查。 |
| 图集坐标 | 图片缩放／裁切时同步更新atlas和Mesh UV | 使用Spine图集打包流程；不能只裁PNG不更新坐标。 |
| 透明格式 | PNG透明通道、PMA处理与atlas标记一致 | 沿用已跑通的导出和打包流程。 |
| 解码位置 | 主像素数据优先PSRAM | 当前分配器失败后仍可能尝试默认内存；管理数据和任务栈可能在内部RAM。 |
| 解码内存公式 | 宽×高×4字节，RGBA8888 | 压缩PNG文件大小不是运行时贴图内存；还要预留解码过程及其他资源。 |
| 屏幕限制 | 320×320，最终RGB565 | 大贴图不能增加屏幕像素；细线和低对比细节要用原生预览检查。 |

## 5. 图集尺寸速查

| 图集尺寸（像素） | RGBA主像素内存 | 适用建议 |
| --- | --- | --- |
| 512×128 | 256 KiB | 之前056紧缩图集；大幅放大人物时细节可能不足。 |
| 512×256 | 512 KiB | 自制半身有效部件装得下时优先考虑。 |
| 512×512 | 1 MiB | 清晰度起点；重新合理排布部件，不把现有图集拉伸成正方形。 |
| 1024×256 | 1 MiB | 与512×512解码内存相同；长宽形状本身不保证更快。 |
| 1024×512 | 2 MiB | 扩展选择；需检查拍照、语音等同时运行时的PSRAM余量。 |
| 尺寸与显示范围的关系 | 互相独立 | 180×240人物不要求180×240图集；图集存放拆分部件，显示范围由骨骼、缩放和位置决定。 |

## 6. 动作制作与触发要求

| 项目 | 建议／要求 | 当前固件行为 |
| --- | --- | --- |
| 待机动作名 | 必须是idle，大小写一致 | 打包时可将wait重命名为idle，设备必须能找到它。 |
| 讲话动作名 | 先提供talk_start | 当前讲话时track1循环talk_start，track0保留idle；没有该动作不会自动生成嘴型。 |
| 待机循环 | 先做4～6秒自然循环 | 时间是视觉起点，不是提高帧率的保证。 |
| 身体起伏 | 先试屏幕上约1～3像素 | 避免共同父骨骼大幅上下移动带动整个人物。 |
| 头发摆动 | 末端先试约2～6像素 | 按画面效果调整；物理链和透明重叠也要控制。 |
| 讲话关键帧 | 主要给嘴、眼和需要变化的部位打键 | 避免给没有变化的全身姿态增加无必要时间线。 |
| 父骨骼与约束 | 最终结果不变才叫静止 | 没打关键帧的部件，仍可能被父骨骼、权重或物理约束带动。 |
| 挥手、转头等大动作 | 后续逐项添加，单独检查包围范围 | 手和头发不要超出屏幕；大动作可能扩大刷新区域。 |
| 保存动作数量 | 按需要，先交付2个 | 没有经过验证的统一数量上限；存储数量与同时播放计算量不是一回事。 |
| 其他动作如何触发 | 需在固件或工具中配置调用 | 仅在模型中添加动作名，不会自动绑定语音命令或设备状态。 |
| 局部动作与性能 | 有助于控制摆幅和差分发送量 | 当前每帧仍标记全部可见附件重画；本轮不加入附件级局部重画优化。 |

## 7. 导出、兼容与OTA打包

| 项目 | 要求 | 交付检查 |
| --- | --- | --- |
| Spine版本 | 4.2.x；当前验证过4.2.26 | 导出数据与4.2运行库匹配；保留原始.spine工程。 |
| 皮肤 | 包配置中的皮肤必须存在，先用default | 名称与role.json一致。 |
| 源文件 | 工程.spine、原画PSD／分层、.skel、.atlas、透明PNG | .spine和PSD留作修改；运行包使用导出资源。 |
| 图集页面 | 本轮沿用单张PNG页面 | atlas的页面名、附件坐标和PNG尺寸必须一致。 |
| 混合模式 | 优先Normal | Additive、Multiply已支持，但需检查效果和开销。 |
| 当前不支持项 | ClippingAttachment、Screen混合、Dark tint／双色染色 | 制作初版时避开这些功能，设备预检会拒绝不兼容资源。 |
| 设备角色包 | 由现有打包脚本生成mmap格式spine.bin | 不是ZIP，也不是ESP32应用固件。 |
| 包内资源 | role.json、skeleton.skel、skeleton.atlas、texture.png | 包含角色ID／版本、皮肤与显示scale；不能只改扩展名生成。 |
| 包体预算 | 沿用当前小于4 MiB的打包要求 | 核对实际大小与设备角色资源分区；不能只看压缩图片大小。 |
| 上传前 | 运行现有资源预检、核对idle与校验值 | 确认引用、版本、格式和尺寸，再上传后台OTA。 |
| 用户上传流程 | 提交角色spine.bin，再下载到设备 | 人物缩放和贴底通过角色资源／布局参数实现；不必为此改固件。 |

## 8. 上机观察与验收

| 阶段／指标 | 操作／观察目标 | 如何判断 |
| --- | --- | --- |
| 原生预览 | 在320×320、100%显示比例查看 | 脸是否清楚、腰是否贴底、手臂和头发是否完整、字幕是否遮挡。 |
| 第一次测试 | 同一角色先静置120秒 | 使用完整30秒窗口，不拿开机或中途换角色的窗口作稳态结论。 |
| 显示帧率 | 目标每个完整窗口display_fps≥8 | 实际显示看display_fps；draw_fps只表示画面生成速度。 |
| 整帧处理 | frame_work_us平均先争取≤110 ms | 125 ms是8帧周期；110 ms是争取余量的建议，不是另一项保证。 |
| 绘制与准备 | 看draw_us、packet_prepare_us、动作／网格耗时 | 绘制、双核工作、等待和传输可能重叠，不能简单全部相加。 |
| 刷新与发送 | 看original_pixels／dirty和sent_pixels | 一个是重画范围，一个是实际发送范围；只减发送不一定减绘制。 |
| 交互测试 | 对话至少120秒，并测试拍照 | 静置8帧不等于对话8帧；观察语音、触摸、摄像头和角色下载。 |
| 内存观察 | 稳态争取PSRAM≥2 MiB、内部RAM≥16 KiB | 这是此前测试余量目标；拍照等瞬时峰值另查，空闲总量不能代替最大连续块。 |
| 任务栈 | 新绘制／传输任务最低余量争取≥1 KiB | 同时确认没有分配失败、看门狗、重启或新增传输异常。 |
| 单变量调整 | 每次只改尺寸、图集、物理或网格中的一项 | 先达到可接受效果，再逐项增加复杂度。 |
| 清晰度不足 | 先检查脸占屏像素和有效脸图分辨率 | 相同模型与显示尺寸，只换贴图作对照；不要直接全面放大。 |

## 9. 056三版实测参考

| 版本／贴图 | 人物包围范围 | 平均显示FPS | 绘制／整帧／发送 |
| --- | --- | --- | --- |
| 小尺寸居中／512×128 | 约157×183像素 | 7.81 | 45.9 ms／126.1 ms／17,535像素每帧 |
| 大尺寸贴底／1024×256 | 约235×260像素 | 5.95 | 76.5 ms／165.7 ms／43,910像素每帧 |
| 大尺寸贴底／512×128 | 约235×260像素 | 6.23 | 69.5 ms／158.3 ms／43,678像素每帧 |

来源：2026-10-03 COM7三次约125秒静置采集，完整30秒窗口均值；三版都为253骨骼、141物理约束。两种大尺寸版保持骨骼文件与scale相同，贴图缩小后FPS约增加4.6%，解码像素内存减少768 KiB。小版与大版还改变位置和阴影，不是严格单变量尺寸实验。第三组有一处日志交错，统计可读字段；采集没有启动资源名，角色关联根据本会话上传说明。不能用这三组保证自制模型帧率。

## 制作顺序

构图 → 分层 → 少量骨骼绑定 → idle与talk_start → 单张图集 → 原生尺寸预览 → 静置测试 → 对话与拍照测试 → 逐项增加。

**优先让脸拥有足够的屏幕像素，把图集分辨率留给有效部件；控制人物整体范围、透明叠加、网格和约束，再以真机日志决定是否放大。**
