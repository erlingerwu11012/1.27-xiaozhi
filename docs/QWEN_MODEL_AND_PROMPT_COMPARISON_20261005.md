# 阿里模型与自然聊天提示词对比（2026-10-05）

结论：建议把 `qwen3.8-flash` 作为下一轮候选，用对话质量规则、保持原文的用户人格和少量示例一起验收。`qwen3.8-max` 保留作对照。此次没有切换生产默认模型，没有部署业务代码，没有增加运行时二次润色。

## 测试范围与限制

- 使用服务器既有、启用中的阿里上游 API key，直接请求 `dashscope.aliyuncs.com`。密钥仅在服务器进程内使用，未输出或保存到测试记录。
- 自动审批拒绝了发送完整生产提示词的测试，理由是内部提示词与人格的数据外发授权不明确。随后改用新编的公开测试规则、用户截图中已提供的人格与虚构对话。此次不是完整生产链路的验收。
- 用户人格原文在两轮中保持一致：你腹黑、调皮、爱捉弄人。说话带一点坏心眼，喜欢调侃用户，但本质是善意的玩笑。
- 四款模型：`qwen-plus`、`qwen3.8-flash`、`qwen3.8-max`、`qwen3.7-plus`，全部实际调用成功。
- 同轮所有模型使用同一提示词与场景。temperature=0.7、top_p=1.0、max_tokens=600、enable_thinking=false、preserve_thinking=false，无自动重试。
- 共 74 次成功模型调用：56 次闲聊生成、18 次工具选择探针；合计返回 usage 37,731 tokens。不是实际账单核对。
- 每个样本只跑一次，没有统计置信区间。第二轮既更换了提示词，也更换了部分场景，不能把两轮差异当作严格的因果实验。
- 所有回复直接来自主模型，无润色，无 ASR/TTS，无客户真实聊天历史，无设备操作。工具探针没有连接真实 MCP 执行器，没有验证工具执行、结果回传、设备状态或成功后的回复。
- 报告所列耗时是非流式完整响应耗时，不是首字延迟。提示词长度、回复长度、缓存与网络均影响耗时。

## 第一轮：简短规则，三组多轮聊天

每个模型 8 轮闲聊，加 3 个结构化工具选择探针。规则要求不补写事实、遵守用户纠正、闲聊简短、无舞台表演和真实工具调用。

| 模型 | 闲聊完整响应平均耗时 | 本轮观察 |
| --- | ---: | --- |
| qwen-plus | 3.209 秒 | 多次出现动作表演、夸张拟人和无请求建议 |
| qwen3.8-flash | 3.503 秒 | 无“外卖已签收”，但有“废柴”等挤兑、猜测与追问 |
| qwen3.8-max | 2.516 秒 | 把“别教育我”接成“作业没写完…的小孩”，未恰当地收住 |
| qwen3.7-plus | 3.435 秒 | 调侃偏攻击，虚构外卖盒等细节 |

四款模型均返回了正确的音量设置与状态查询 `tool_calls`，在没有摄像头预览工具时均没有改用音量或状态工具。但部分说明文字仍夸张。这三个探针不代表全部工具或自然语言都可靠。

## 第二轮：明确分寸与少量对话示例

人格原文不变。新增规则：人格影响措辞、不要求每句调侃；疲惫、烦躁或反对开玩笑时收住；用户纠正时不顶嘴、不反讽；用示例展示自然接话。每款模型 6 轮，含熟悉场景与新措辞场景。

| 模型 | 闲聊完整响应平均耗时 | 本轮观察 |
| --- | ---: | --- |
| qwen-plus | 1.334 秒 | 缩短了，但仍出现“（小声）”“（停顿两秒）”，并补写台面上的碗 |
| qwen3.8-flash | 0.776 秒 | 大多为一两句，接住“别逗我”；仍补出“一堆碗”及未经请求的建议 |
| qwen3.8-max | 1.151 秒 | 更能收住调侃；仍有“原地升天”等夸张比喻，也擅自假定明天能安装好 |
| qwen3.7-plus | 1.481 秒 | 有改善，但仍主动劝说，并在纠错探针中用“幻觉”挤兑用户 |

第二轮最后一句“我说洗碗机明天才到，你怎么说我已经用上了？”是用户带有未获当前历史支持的前提的探针：此前合成历史中，助手并没有说用户已用上洗碗机。因此不能据此声称模型在前文真的编造了已使用事实；它用于观察处理用户纠正与不支持前提时，是否继续补写未知事实或攻击用户。

### 部分未经改写的实际输出

用户：别给我灌鸡汤，也别给方案，就随便聊两句。

- qwen-plus：行，鸡汤撤下，方案回收，连同我的小算盘一起关进抽屉。\n——现在，只剩一句实话：累就对了，说明你今天确实活过。
- qwen3.8-flash：行，那就不聊那些有的没的。
- qwen3.8-max：行，那就一起瘫会儿。今天确实够呛的。

用户：我点了外卖，吃完洗澡，然后躺着。

- qwen3.8-flash：这流程听着就舒坦，连“明天再说”都省了。
- qwen3.8-max：外卖、洗澡、躺平，标准的回血三件套。等会儿吃饱了往那一瘫，估计能直接原地升天。

用户：你又在挤兑我了，今天别逗我。

- qwen3.8-flash：行，不逗了。今天就这样吧，别逼自己硬撑。
- qwen3.8-max：好，不逗了。今天辛苦了。

## 示例提示词下的追加工具选择检查

仅对两款 Qwen3.8 再查 3 个相同探针，合计 6 次调用：

| 请求 | Flash 与 Max 的结果 |
| --- | --- |
| 声音小一点，调到30吧 | 返回 self_audio_speaker_set_volume，JSON 参数 volume=30，无执行前正文 |
| 先别调音量，我就问问现在是多少 | 返回 self_get_device_status，未调用设置音量工具，无执行前正文 |
| 打开摄像头让我看实时画面 | 无工具调用，如实说明目前做不了 |

这证明此次样本返回的是原生结构化工具调用，而非正文假装调用。真实设备/MCP执行和异常恢复仍需另行回归。

## 借鉴哪些开源项目

1. [Promptfoo](https://github.com/promptfoo/promptfoo)：建立固定多轮测试集，比较模型与提示词、重复采样、保存原始结果。评测应包含事实一致性、用户负反馈、人格分寸、工具选择及失败结果后的回复。
2. [DSPy / GEPA](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/getting-started/gepa-optimization.md)：用样本和评分反馈自动搜索更好的提示词。保留独立训练、验证、最终测试集；最终测试不能参与挑选提示词。只优化平台规则和示例，用户人格字段冻结。
3. [ms-swift](https://github.com/modelscope/ms-swift)：需要真正调整模型权重时，借鉴 SFT、LoRA、DPO 的流程。需有可训练模型、合适数据与训练/部署资源；现有商业模型 API key 本身不提供修改其权重的能力。

所谓“训练提示词”，建议先采用第 2 种：候选提示词生成、批量测试、评分、保留较好的候选。优化阶段可以使用模型分析失败原因，上线仍只运行一个主模型，不增加语音二次润色。

建议起步人工整理约 100–200 组代表性的多轮合成或获授权对话，标记喜欢/不喜欢与具体原因。数量是实施起步建议，不是有效性保证。包含多个用户人格，避免只对“腹黑”或这几句话有效。评估不能仅靠关键词或另一个模型评分，保留人工盲评。

## 下一步建议

先选 Qwen3.8-Flash 作候选、Max 作对照，固定用户人格，通过数据驱动的提示词优化找表达分寸。候选通过独立新场景与重复测试后，再用完整生产提示词、真实工具目录、MCP/设备与语音链路验收。

正式切换要同步网关模型目录、硬件计费校验和后端模型配置，明确思考模式及历史消息格式；不能只替换 model 字符串。此次没有变更这些配置。

如上述步骤仍达不到要求，再考虑针对对话质量进行 SFT/DPO 微调。训练目标是更好的接话方式、事实边界与工具行为，用户运行时依然选择自己的人格。
