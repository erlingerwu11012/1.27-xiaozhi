# 给 Cursor 的实施计划：修复录入任务的 PSRAM/Flash 边界并释放内部 SRAM

请按以下计划实施第一轮修复。目标是让人脸录入、认人和识图稳定运行，保留现有语音、屏幕、触摸和雷达功能。不要把任务扩大成全项目内存重构。

## 1. 目标与范围

本轮完成三项改动：

1. 隔离人脸录入及清理任务中的 NVS/Flash 访问，避免 PSRAM 栈直接执行会关闭缓存的操作。
2. 关闭未使用的图形计时统计，消除重复的内部 SRAM 静态占用。
3. 改善周期诊断任务的栈余量和分配方式，保留后续验证需要的日志。

随后编译、检查内存变化，并在用户安排的设备测试中验证功能。没有实机测试的部分必须标记为未验证，不得宣称已经解决重启或保证语音零影响。

### 本轮禁止改动

- 不迁移、不缩小 Opus 栈；保持音频参数、优先级、核绑定和队列策略。
- 不改变录入状态机、语音提示、采集间隔、姿态顺序、候选图片数量和成功/失败判定。
- 不改变接口 URL 规则、认证方式、请求字段、响应字段、重试/超时规则和 V1/V2 兼容行为。
- 保留 `pose`、`round`、`candidate_0/1/2` 等现有 multipart 字段及现有一次请求提交多张候选图的方式。
- 不改 multipart 为流式上传，不改 `GetLastJpeg()` 语义，不改 JPEG 旋转算法或画面质量。本轮先减少变量。
- 不断开或暂停 WebSocket，不降低语音可用性。
- 不把 USB/LCD/I2S DMA 缓冲、描述符、TCB 或系统驱动任务统一搬到 PSRAM。
- 不开启全局任务栈迁移、Flash 自动挂起或 PSRAM XIP 来绕过问题。
- 不关闭断言、栈保护、TLS 证书校验，不通过吞掉错误掩盖失败。
- 不提交、回退、覆盖工作区已有的无关改动，不刷机、不擦 NVS；设备测试/刷机按用户后续明确安排执行。

## 4. 步骤 B：关闭无实际用途的图形计时统计

为 `helper.h` 内的计时统计提供默认关闭、在所有使用该头文件的编译单元中一致生效的编译开关。

- 关闭时不要定义 `_timerStack`、`_classifiedStatistics` 及对应计时状态，避免构造函数让无用对象仍被链接保留。
- `BENCHMARK_CLASS_START/END/RESET/REPORT` 关闭时不做计时或分配。
- 特别注意：`BENCHMARK(code)` 关闭时仍必须执行 `code` 一次，不能误删被包裹的业务操作。
- 保持宏与现有调用语法兼容，尤其是现有调用没有尾随分号的情况。
- 不删除或改变渲染、脏矩形、纹理、Spine、帧率和屏幕传输逻辑。
- 如果保留开启调试模式，确保开启后可编译；本轮不需要重构该调试系统。

验证：检查新 ELF/map，确认默认关闭时上述重复对象不再占用内部 SRAM；报告实际静态 RAM 差额，而不是只按源码推算。

## 5. 步骤 C：给人脸配置增加内部栈执行边界

推荐采用局部、同步的配置访问执行器，保留每次读取最新配置/凭证的现有语义，避免新增长期缓存造成凭证过期。

### 执行方式

- 建立一个范围仅覆盖人脸配置访问的执行器任务，使用内部 SRAM 栈。不要把全部 `Settings` 调用全局重定向。
- 初始内部栈预算为 4–6KiB，最终按最深 NVS 操作和日志调用的实测余量决定，不能为省 RAM 硬压栈。
- 支持的操作保持有限：读取配对凭证、加载人脸能力配置、保存能力配置、清除能力配置。
- `Settings` 对象的创建、所有 NVS 读写、提交、关闭，都在执行器中完成。不要把一个 NVS handle 打开在内部任务后，再交给 PSRAM 任务继续使用。
- 对调用者保持同步获取结果的语义；返回值和请求数据可以存放在普通内存/PSRAM，但执行 Flash 操作的栈必须是内部栈。
- 执行器只做配置 I/O，不拍照、不执行 HTTPS、不调用录入状态机或 UI，不反向获取 `FaceEnrollmentClient` / manager 的业务锁。
- 在启动人脸业务前明确初始化该执行器；初始化失败时人脸功能返回既有可处理错误，不能继续从 PSRAM 栈直接读 NVS。

### 必须覆盖的调用链

- `CreateSession()` 的能力配置延迟加载和 `LoadPairingToken()`。
- V1 `UploadFrame()`。
- V2 `AssessFrame()` / `CapturePose()` 经由 `PostGuidedMultipart()` 的凭证读取。
- `CancelSession()`，包括 `face_enroll_cln` 异步清理、超时、取消后迟到成功的清理。
- `GetCapability()` / `HasValidCapability()` / `IsGuidedBurstV1()` 内部的延迟加载。
- 无效持久化配置的清除、`SetCapability()` 的保存、`ClearCapability()` 的清除。
- 审计这些入口的回调和错误分支，确认没有遗漏直接或间接 NVS/Flash 操作。

### 并发和生命周期要求

- 不允许在等待执行器时形成锁环；执行器不得等待正在等待它的主事件任务。
- 队列满、分配失败、初始化失败必须按现有错误规则返回，不回退到调用者直接执行 NVS。
- 请求、结果和完成通知必须有明确所有权。取消/等待超时后，执行器不得写入已经离开作用域的栈变量。
- 保留现有代次校验、迟到结果丢弃、取消清理和“已成草稿不 DELETE”的语义。
- 凭证更新、解绑、能力配置失效后，后续请求仍须看到正确状态；不能永久缓存第一次读出的 token。
- 不改变 NVS namespace/key、数据格式、持久化策略；不新增 token 持久化位置。
- 日志不得打印 token、JPEG 内容、完整带查询参数 URL 或原始服务端响应。

如果发现项目已有等价且安全的内部栈配置执行器，优先复用，不重复建任务。若使用其他实现，必须逐条证明满足上述边界及语义，不能只修首次创建会话。

## 6. 步骤 D：改善诊断任务，保留排查能力

- 检查 `LogCpuAndMemory()` 的 `TaskStatus_t tasks[48]`、CPU 排序数组及嵌套调用，把大块临时数据改为有明确所有权的 PSRAM 工作区。
- 周期诊断任务可使用 PSRAM 栈；保持日志内容、采样意义和周期，不改变音频/UI任务配置。
- 迁移前核对完整诊断调用链没有 Flash/NVS 访问；使用正确的创建/删除配对接口。
- 不增加任务数量，不因统计逻辑共享缓冲而引入并发覆盖。
- PSRAM 工作区分配失败时跳过本次非关键统计，不能回退申请大块内部 SRAM，也不能让设备 abort。
- 保持任务数变化时的数组容量检查；容量不足应可识别地跳过/扩容，不能越界或误报为空任务表。
- 修复目前仅 280 字节的栈余量，不能把同样紧张的调用链原样搬走后宣称问题解决。
- 新增/修改的执行器和诊断任务，实测栈历史余量以至少 1KiB 为初始验收目标，并覆盖深调用与错误路径；这个值不作为所有系统任务的统一阈值。

必要时记录失败分配的大小、能力标志和调用位置。分配失败回调不得再分配内存、阻塞或递归调用复杂日志；优先使用轻量记录后由普通任务输出。

不要把“内部最大块大于 20KB”或“待命日志正常”当作成功标准。阈值必须对应实际失败分配及最坏场景，且保留余量。

- 若仍重启，先用匹配 ELF 解析 backtrace，区分 Flash/外部栈、栈溢出、堆耗尽和越界，不能自动归因于第二条 TLS。

## 9. 内存预算和后续边界

- 删除计时统计的参考收益：15,780 字节，须以新旧 map 差额确认。
- 诊断任务迁栈的参考收益：原内部栈约 4KiB；移出局部数组本身不等于释放已分配的整个栈。
- 新增配置执行器会消耗内部栈约 4–6KiB，以及 TCB、同步结构等开销，必须扣除。
- 因此本轮不能继续声称释放约 51KiB；那个估算包含本轮不做的 32KiB Opus 迁栈。采用新执行器时，净收益粗略约 13–15KiB，再减其他实际开销。
- 释放总量不等于最大连续块增长；本轮还解决了与容量无关的 Flash/外部栈调用问题。

若第一轮实测稳定，停止扩大改动范围。若仍缺内存，提交具体阶段的峰值和失败分配证据，再单独规划：图像所有权、multipart 分段发送、JPEG 内部工作区或 Opus 迁栈。不要在本轮顺手实施。
